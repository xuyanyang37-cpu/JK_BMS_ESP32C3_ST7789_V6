# 协议运行逻辑与接口审计（2026-10-09）

## 数据调用链

1. `BmsBle::notifyCallback()` 接收 BLE 通知。
2. `BmsBle::handleNotification()` 将通知拼入固定 RX 缓冲区，清理旧 ACK/噪声。
3. `BmsProtocolManager::findFrameStart()` 找到缓冲区中最早的候选帧头。
4. `BmsProtocolManager::frameLength()` 由该候选协议计算完整帧长。
5. 收到完整帧后调用 `BmsProtocolManager::parseFrame()`。
6. 只有具体协议返回成功，才提交 `activeProtocol_`；后续轮询命令继续使用已确认协议。
7. 解析器更新 `BmsData`，显示层和网页层读取数据。

## 本次修正

- 修正管理器在遍历多个协议时，后找到的协议会覆盖最早帧头对应协议的问题。
- 将“当前缓冲帧候选解析器”与“已确认的活动协议”分开；无效帧不应改变后续命令使用的活动协议。
- TT 增加显式变长帧长接口：Modbus 正常响应根据 byte-count 计算；异常响应固定按 5 字节；EF 私有帧按长度字段计算并限制上限。
- JK 4E57/TLV 解析先保留 MAC、网页配置和启动状态等本机字段，再清零本帧遥测字段；避免原先新建空 `BmsData` 导致本机状态丢失，也避免缺失 Tag 时沿用上一帧遥测值。

## 仍需注意

- `JbdProtocol` 和 `DalyProtocol` 当前仍是预留/空实现，不应当视为已完成的可用协议。实现真实解析前需要对应保护板原始通知抓包或可靠协议文档。
- ANT 解析虽有实现，但命令发送、CRC 覆盖区间、帧长度和每个字段的偏移仍应使用实际设备抓包验证。
- TT 的寄存器数量、寄存器含义、温度/电流缩放和 EF 私有帧格式必须与目标板实测一致。
- 彦阳 Modbus 当前固定读取从站地址、寄存器起始地址/数量及缩放方式；需要以设备实际应答验证，不能仅凭编译成功认定数据正确。
- CI 的 PlatformIO 编译只验证编译/链接，不会验证 BLE 订阅、硬件屏幕、协议 CRC、字段单位或断线恢复状态机。

## 建议的硬件验收

1. 保存一组真实 BLE 通知十六进制日志，覆盖拆包、粘包、噪声前缀和断线重连。
2. 对每种协议分别验证帧头、声明长度、CRC/校验和、解析成功/失败结果。
3. 对照 BMS 屏幕或原厂 App 验证总压、电流方向、SOC、电芯数、温度和容量单位。
4. 验证无效帧不会切换协议；断线后必须在收到有效数据后才清零恢复失败计数。
5. 验证热点模式不会重复创建 WebServer 或反复分配 BLE 客户端。
